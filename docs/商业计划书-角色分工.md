# Synapse 项目商业计划书：角色分工与工作量

## 1. 估算口径

本项目的研发工作量以 **原型项目 Synapse + 重构项目 SynapseV2 的累计交付工作** 为基础估算，合计按 100% 计。原型项目承担了产品可行性验证和第一版工程基础；重构项目在保持核心行为连续性的基础上，完成了架构收敛、跨平台复用、功能扩展和交付验证。

这里的比例表示各角色承担的**综合工作量与责任范围**，不是简单按代码行数、文件数量或投入人数计算。产品设计、技术方案、开发、联调、测试和文档等工作按其最终交付责任归属进行分配；同一项成果只计入一个主责角色，避免重复计算。

## 2. 角色分工总览

| 角色 | 工作量 | 主要定位 | 主要交付结果 |
| --- | ---: | --- | --- |
| 角色一：产品与学习业务架构负责人 | 30% | 定义产品价值、学习闭环和业务规则，并统筹两代项目的演进 | 产品流程、学习计划、澄清问答、复习闭环、作业排期、知识图谱等核心业务方案 |
| 角色二：核心技术与 AI 能力负责人 | 30% | 负责后端/核心引擎、模型接入、数据与算法能力 | 原型版 FastAPI/SQLite/知识图谱/模型工作流，以及 V2 TypeScript core、Provider、检索和离线降级 |
| 角色三：客户端与跨平台产品负责人 | 25% | 将核心能力转化为可使用、可部署的多端产品 | 原型 React 前端，以及 V2 Web 与微信小程序 UI、平台适配、图谱可视化和资料/作业等页面 |
| 角色四：质量保障与交付运营负责人 | 15% | 负责可验证性、稳定性、发布准备和项目文档 | 黄金样本、单元测试、E2E 测试、类型检查、构建验证、README/架构文档和交付边界说明 |

合计：**30% + 30% + 25% + 15% = 100%**。

## 3. 角色一：产品与学习业务架构负责人（30%）

### 核心职责

- 将“AI 学习陪伴”拆解为可执行的用户流程和产品模块。
- 定义从用户目标输入，到澄清、计划生成、每日执行、打卡、复习和反馈的完整学习闭环。
- 设计自由计划、积木计划、三层计划、多科目合并、课程表避让、作业截止管理等业务规则。
- 明确离线规则模式、AI 生成标识、资料证据和 AI 依据展开等产品口径。
- 统筹原型版功能向重构版的迁移，确认新增能力不破坏原有行为和数据连续性。

### 对应项目成果

- **原型 Synapse**：确定 AI 学习助手的核心交互、学习计划、知识图谱检索、会话流程和数据闭环。
- **重构 SynapseV2**：将原型能力扩展为课程表、资料库、BM25 本地检索、SM-2 复习队列、作业式计划、知识图谱掌握度、学情周报和证据展开。

### 商业价值

该角色确保技术投入始终围绕用户可感知的学习效率提升，形成区别于普通聊天机器人的“目标—计划—执行—复习—诊断”产品壁垒。

## 4. 角色二：核心技术与 AI 能力负责人（30%）

### 核心职责

- 负责原型后端、业务编排、数据持久化和知识图谱检索能力。
- 实现 DeepSeek 等模型的调用、工具调用、结构化输出、失败降级和流式协议。
- 完成从 Python 多运行时到 TypeScript 单核心的技术重构。
- 设计 `protocol`、`domain`、`application`、`providers`、`storage` 和 `ports` 的分层边界。
- 实现计划算法、澄清状态机、资料抽取、BM25 检索、知识图谱构建、SM-2 调度和作业排期。
- 保证核心逻辑与平台无关，便于 Web、小程序、桌面和 Android 后续复用。

### 对应项目成果

- **原型 Synapse**：FastAPI、SQLite/SQLModel、仓储层、知识图谱、LangChain/LangGraph 工作流、DeepSeek 接入和 React API 支撑。
- **重构 SynapseV2**：`packages/core` 单一核心、KV 存储、模型 Provider 抽象、离线规则模式、资料到图谱再到复习的幂等链路，以及 Web/小程序共享协议。

### 商业价值

该角色沉淀可复用的核心引擎，降低未来接入新模型、新平台和新数据存储的边际成本，形成项目的技术资产和扩展能力。

## 5. 角色三：客户端与跨平台产品负责人（25%）

### 核心职责

- 负责原型 Web 前端和重构版 Web、小程序的页面、交互及状态呈现。
- 将 core 的计划、资料、课程表、作业、复习、仪表盘和知识图谱能力转化为完整用户体验。
- 实现响应式 Web 布局、移动端导航、小程序页面和平台差异化适配。
- 负责 SVG 图谱、Canvas 图谱、文件选择、PDF 文本抽取、二维码作业包等客户端能力。
- 保持 Web 与小程序在业务行为上的一致，同时遵循各平台的交互和 API 约束。

### 对应项目成果

- **原型 Synapse**：React/Vite 学习助手前端、设置页、聊天界面、计划卡片、任务执行和后端 API 联调。
- **重构 SynapseV2**：Vite + React Web 单页应用、Taro 微信小程序、资料库、课程表、作业清单、复习提示、图谱可视化、仪表盘和数据导出。

### 商业价值

该角色直接决定产品的可用性、留存体验和多端覆盖能力，使同一套核心能力可以触达浏览器和微信小程序用户。

## 6. 角色四：质量保障与交付运营负责人（15%）

### 核心职责

- 建立原型行为基线和重构后的黄金样本，保障迁移前后协议与核心行为可比。
- 负责核心单元测试、边界测试、压力测试、Web Playwright E2E 和构建验证。
- 验证知识图谱、演示数据、资料转复习等流程的幂等性，防止重复数据和重复任务。
- 负责 TypeScript 类型检查、Web/小程序构建、平台冒烟和发布前检查。
- 维护 README、架构文档、功能状态、能力边界和部署说明。
- 记录尚未交付的桌面、Android、云 AI、推送和跨设备同步等范围，避免商业计划过度承诺。

### 对应项目成果

- **原型 Synapse**：后端测试、前端联调、启动脚本、版本文档和重构前的工程状态梳理。
- **重构 SynapseV2**：core 分层测试（domain / 流程 / 压力）、Web E2E、类型检查、vendor 边界检查、生产构建和仓库文档治理。

### 商业价值

该角色把研发成果转化为可演示、可验收、可维护和可持续迭代的交付物，降低上线风险并提高对外沟通可信度。

## 7. 协作与责任边界

四个角色采用“主责 + 协作”的方式推进：

1. 角色一负责需求优先级和业务验收口径。
2. 角色二负责核心技术方案和跨平台业务一致性。
3. 角色三负责界面、交互和平台交付体验。
4. 角色四负责证据、质量门禁、文档和发布验收。

涉及跨角色事项时，由角色一确认产品取舍，角色二确认核心接口，角色三完成平台呈现，角色四补齐测试与交付记录。这样既覆盖原型到重构的全部工作，也避免把同一项工作重复计入多个角色。

## 8. 当前阶段与后续投入

现阶段已完成原型能力验证，以及 V2 的 Web 和微信小程序主链路交付。后续新增投入主要集中在桌面/Android 壳、微信真机验收、云端 AI Provider、推送提醒、账号体系、跨设备同步和数据恢复等方向；这些工作应继续沿用上述四角色分工，并在新增版本中单独核算，不回溯调整本章节的历史工作量比例。
